# Architecture and Design Decisions

## Sprint 3 Authentication Decisions

### DTOs at the HTTP boundary

Controllers accept and return dedicated DTOs, not JPA entities. This permits request-specific validation, keeps persistence mappings from becoming a public contract, and prevents accidental exposure of fields such as `passwordHash`. It also lets the API evolve independently of the database model.

### Password hashing

Passwords are one-way BCrypt hashes via Spring Security's `BCryptPasswordEncoder`; they are never encrypted for later recovery, logged, or returned. BCrypt is an adaptive password hash designed for password storage. Login uses `PasswordEncoder.matches(rawPassword, storedHash)`.

### JWT and stateless bearer authentication

LedgerFlow issues signed, short-lived JWT access tokens. A token has standard `sub` (the user's UUID), `iat`, `exp`, and `iss` claims only. JWT payloads are encoded, not encrypted, so no password, hash, or other sensitive data is included. Spring Security's resource-server JWT support validates bearer tokens and sets the authenticated principal; sessions are disabled. This avoids a custom filter and keeps token validation in the current supported integration.

### Token lifetime and secret handling

The access-token expiration is externally configured through `JWT_EXPIRATION` (15 minutes in the development configuration). The HMAC signing secret is required from `JWT_SECRET`; it is never committed. A sufficiently long random secret must be provisioned by each deployment environment and rotated through deployment configuration.

### Authentication provider scope

Login uses the application service to fetch a user and compare its BCrypt hash. `UserDetailsService` and `DaoAuthenticationProvider` are Spring Security's database-backed username/password mechanism, but are not needed for this JSON login endpoint. The resource server authenticates JWTs after login. A future form-login or reusable username/password authentication flow can add a `UserDetailsService`/`DaoAuthenticationProvider` without changing this API.

### Transactional registration

Registration is one transaction because the business invariant is exactly one wallet for every new user. A wallet failure rolls back the user insert as well as the wallet work; a transaction annotation is verified by an integration test that forces wallet provisioning to fail.

### Status-code choices

Registration returns `201 Created`; a duplicate email returns `409 Conflict`; DTO validation returns `400 Bad Request`. Both unknown-email and wrong-password login attempts return `401 Unauthorized` with the same generic message, avoiding unnecessary account-existence disclosure. Missing or invalid bearer tokens also return `401`.

## Sprint 2 Design Decisions

### 1. ID Strategy

**Decision:** Use UUID primary keys for both `User` and `Wallet`.

**Reason:** UUIDs can be generated by the application, are safe to expose in future APIs, and avoid predictable sequential identifiers. They also make later data imports or multi-instance writes easier because IDs do not require coordination with one database sequence.

**Trade-offs:** `Long` keys are smaller, more index-friendly, and easier to inspect manually. UUID indexes are larger and random UUID values can be less cache-friendly. Those costs are acceptable at LedgerFlow's current scale, while UUIDs avoid an unnecessary future migration away from externally guessable IDs.

### 2. User-Wallet Relationship

**Decision:** Model the relationship as bidirectional: `User` has one `Wallet`, and `Wallet` belongs to one `User`. `Wallet` owns the relationship through a non-null, unique `user_id` foreign key.

**Reason:** The wallet table is the natural place for the foreign key. A unique foreign key enforces that a user cannot have two wallets. The inverse `User.wallet` navigation is useful for the core domain without making `users` depend on a wallet-table column. The `User.assignWallet(...)` method keeps both in-memory sides aligned. Cascading is limited to `PERSIST` and `MERGE` from User to Wallet, because a wallet has no useful lifecycle outside its user; removal is deliberately not cascaded until account-retention rules are designed. Both associations use lazy fetching to avoid loading the other aggregate accidentally.

**Trade-offs:** A normal unique foreign key represents “at most one wallet per user”; a database row in `users` alone cannot prove “at least one wallet” without a more complex shared-primary-key or deferred-constraint design. LedgerFlow enforces creation of the pair through the domain method and will add service-level lifecycle rules in a later sprint. Bidirectional mappings also require keeping both sides synchronized, which is why association management is centralized on `User`.

### 3. Money Representation

**Decision:** Store wallet balances as `BigDecimal`, mapped to `NUMERIC(19,2)`.

**Reason:** `double` is binary floating point and cannot precisely represent many decimal monetary values, which can produce rounding errors. `BigDecimal` is decimal and, together with a fixed database precision and scale, preserves INR balances exactly to paise.

**Trade-offs:** `BigDecimal` needs explicit scale and rounding rules in calculation code and is slower than primitive arithmetic. Correctness and auditable financial values matter more than that small overhead.

### 4. Status Representation

**Decision:** Use Java enums stored as strings with `@Enumerated(EnumType.STRING)`.

**Reason:** A `User` may be `ACTIVE`, `SUSPENDED`, `BLOCKED`, or `DEACTIVATED`. A `Wallet` may be `ACTIVE`, `RESTRICTED`, or `CLOSED`. String storage remains understandable in PostgreSQL and does not change the meaning of existing values if an enum is reordered.

**Trade-offs:** String values use more space than ordinal integers and renaming an enum constant requires a data migration. The explicit, stable values are safer and more maintainable than ordinal persistence.

### Implementation Notes

- `passwordHash` records a password hash only; plaintext passwords must never be persisted.
- Email is required and unique. Phone is optional contact data and is not currently a login identifier or a database-unique field.
- Spring Data JPA auditing supplies `createdAt` and `updatedAt` as UTC `Instant` values. Application code does not set them manually.
- The initial currency is constrained by the `WalletCurrency` enum to `INR`; it is deliberately not a free-form string.
